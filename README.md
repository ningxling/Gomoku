# Gomoku · 传统搜索 + 强化学习 的双引擎五子棋

一个可以在浏览器里下棋的五子棋项目，包含**两套 AI 实现**：

| 引擎 | 实现方式 | 依赖 |
| --- | --- | --- |
| **传统搜索** | α-β 迭代加深 + 棋型评估 + 威胁表 + VCF 算杀 + 禁手判定（纯 Python，手写） | 无（标准库） |
| **强化学习** | AlphaZero 风格：策略价值网络 + PUCT 蒙特卡洛树搜索 + 自我对弈训练 | torch（CPU 即可） |

网页上可以自由切换，还支持**传统 AI vs 强化 AI 自动对战观战**。项目同时包含一套完整的
训练流水线：远程训练、权重自动回传、基准赛、健康监控、权重存档。

> 这是北京大学《数据结构与算法》课程大作业项目。仓库中的 `gomoku/game.py`、`model.py`、
> `mcts.py`、`train.py`、`server.py` 与 `gomoku.html` 的初版来自开源项目 kimi3 的五子棋实现，
> 本项目在其上做了大量修改与扩展，详见 [来源与 AI 使用声明](#七来源与-ai-使用声明)。

## 一、项目背景与目标

**为谁解决什么问题**：五子棋 AI 有几个经典做法——搜索（α-β）擅长精确读杀但不擅长"大局观"，
神经网络擅长棋感但需要海量算力。这个项目的目标是把两条路线都实现出来，并**在同一套界面上
做可控对比**，回答几个具体问题：

1. 只用课程里的数据结构与算法（位/窗口编码、哈希表、α-β 剪枝），能做出多强的五子棋 AI？
2. 只有 30 万参数、4 核 CPU 的强化学习模型，能不能追上传统搜索？
3. 每一步的性能瓶颈在哪，怎么用实验而不是直觉来判断？

**已完成的核心功能**

- [x] 三种对局模式：人人对战 / 人机对战（可选传统或强化）/ 传统 vs 强化自动观战（可暂停）
- [x] 传统引擎：19×19 中局 0.3 秒可搜到 **5 层**、约 6000 节点，含 VCF 强制杀
- [x] 强化引擎：策略价值网络 + MCTS，199 个 ELO 级权重版本存档
- [x] 完整训练流水线：远程训练 → 权重回传 → 自动基准赛 → 曲线记录
- [x] 自动化运维：进程守护、卡死检测、每小时健康巡检、30 分钟权重快照
- [x] 自测脚本：棋规、禁手、算杀、自对弈合法性、HTTP 协议、双引擎服务、AI 对战流程

## 二、课程知识与核心设计

### 2.1 传统引擎（`gomoku/engine.py`，约 700 行）

**数据结构：长度-5 窗口 + 三进制编码**

19×19 棋盘在 4 个方向上一共有 **1020 个"长度 5 的窗口"**（横 285 + 竖 285 + 两斜各 225）。
每个窗口用 5 位三进制数编码（0 空 / 1 黑 / 2 白），取值范围 0~242，直接作为查表下标：

```
窗口分值表   _TB[243] / _TW[243]   成五=10^7, 四=2000, 活三=200, 二=20, 一=2
冲四标记表   _FOUR_MASK[243]       该窗口是否"4 子 + 1 空"（即存在成五点）
```

落子时**只更新包含该点的 20 个窗口**（每个方向 5 个），所以

> 单次落子/撤销的评估代价是 O(20)，而不是 O(棋盘面积)。

这是本项目的核心数据结构设计，也是它能用纯 Python 跑到每秒上万节点的原因。

**威胁表（增量维护）**

`tcnt[player]` 是一个计数器：记录"哪些空点能让该方下一手成五"。窗口变成"4 子 + 1 空"时
给它对应的空位 +1，被破坏时 -1。于是每个搜索节点都能 O(1) 判断：

- 自己有冲四点 → 直接返回必胜分（不必搜索）
- 对方有冲四点 → 只能挡（挡点唯一时只搜这一手）

**搜索：α-β + 置换表 + 迭代加深**

- negamax + α-β 剪枝，迭代加深 2→10 层，超时抛异常回退到上一层
- Zobrist 哈希 + 置换表（EXACT / LOWER / UPPER 三种标记）
- 候选点按"进攻分 + 0.9×防守分"排序（分数来自窗口增量，落子前 O(20) 算好）
- 叶子节点做"强制着法延伸"（伪静息搜索）：对方有四时再多搜一层

**VCF 算杀**：连续冲四搜索，只在"我方四子点"上展开，深度 6，能找到 5~10 步内的强制胜。

**禁手判定**（黑棋）：长连 / 四四 / 三三。实现方式是在落点周围取 9 格线段，枚举每个空位
"补上后是否形成五连 / 活四"来计数，因此能识别**跳三、跳四**（网页端只识别连续棋形，比本实现宽松）。

### 2.2 强化学习引擎（`gomoku/model.py` + `mcts.py` + `train.py`）

- **网络**：3 通道输入（己方子 / 对方子 / 先后手）→ 64 通道 3×3 卷积 → 4 个残差块 →
  策略头（1×1 卷积，每格一个 logit）+ 价值头（全局平均池化 + 全连接）。共 **298,246 参数**。
  全卷积结构使权重与棋盘尺寸无关。
- **搜索**：PUCT 蒙特卡洛树搜索（`c_puct=1.5`），先验来自网络策略，叶值来自网络价值。
- **训练**：自我对弈生成 (局面, MCTS 策略, 终局结果) 三元组 → 策略交叉熵 + 价值 MSE。
  加入了三处工程改造（见 `docs/AI协作记录.md`）：
  1. **根节点战术护栏**：能成五 / 唯一挡四时直接走，不跑 MCTS（π 变成精确标签）
  2. **截断局 bootstrap**：对局超时截断时不再标"和棋 0"，而是用传统引擎的搜索值当目标
  3. **颜色镜像增强**：每条样本额外生成"交换黑白"版本，保证训练集颜色对称

### 2.3 复杂度与代价分析

| 操作 | 代价 | 说明 |
| --- | --- | --- |
| 落子 / 撤销 | O(20) | 只更新 20 个窗口 + 邻域计数 |
| 静态评估 | O(1) | 维护总分 `score[black] - score[white]`，直接用 |
| 单点排序分 | O(20) | 20 个窗口的查表增量 |
| 威胁表维护 | O(40) | 20 个窗口 × 2 个玩家 |
| 单节点（生成+排序+落子） | 约 50~80 μs | 实测约 1.2~2 万节点/秒 |

空间：窗口表 1020×5 个索引、每格 20 个窗口引用、置换表上限 30 万条。

- Python **3.9+**（开发与测试用 3.9 / 3.14）
- 只有"强化学习"部分需要 `torch` 和 `numpy`；**传统引擎只用标准库**

```bash
pip install -r requirements.txt      # numpy + torch(CPU)
```

> 只玩传统引擎时可以跳过 torch：`server_ab.py` 不 import torch。

### 3.2 启动（两种 AI 都可切换）

```bash
cd gomoku
python play_all.py            # 打开 http://localhost:8000 并自动开浏览器
```

Windows 下也可以直接双击仓库根目录的 `开始游戏.bat`。

```bash
cd gomoku
python play_ab.py --time 1.5
```

| 算杀 | 活三做出活四（VCF） |

| 自对弈 | 9×9 4 局 + 15×15 2 局，无非法着法、无禁手着法 |

| AI 对战 | 两引擎交替下完整一局，无报错、无非法落子 |

### 5.2 消融实验：三个部件各值多少

完整数据见 [`docs/ablation_result.md`](docs/ablation_result.md)，由 `tools/ablation_engine.py` 生成：
19×19、限时 0.3 秒、3 个 10 子安静开局取平均；9×9 快棋 0.05 秒/手、各 8 局交替先后手。

**搜索规模**

| 配置 | 平均深度 | 平均节点数 | 平均耗时 |
| --- | ---: | ---: | ---: |
| 完整版 | **5.0** | 5,973 | 312 ms |
| 去掉置换表 | 5.0 | 5,888 | 307 ms |
| 去掉 VCF | 5.0 | 6,059 | 306 ms |
| 去掉威胁表 | **2.7** | 2,901 | 313 ms |

**战术正确性**

| 配置 | 一步成五 | 挡唯一冲四 | 活三算杀 |
| --- | :---: | :---: | :---: |
| 完整版 | ✅ | ✅ | ✅ |
| 去掉 VCF | ✅ | ✅ | ❌ |
| 去掉威胁表 | ✅ | ✅ | ❌ |

**自对弈强度（对完整版）**

| 配置 | 胜 | 负 | 和 | 胜率 |
| --- | ---: | ---: | ---: | ---: |
| 去掉置换表 | 1 | 3 | 4 | 38% |
| 去掉 VCF | 4 | 4 | 0 | 50% |
| 去掉威胁表 | 0 | 4 | 4 | **25%** |

**结论（自己的判断）**

1. **威胁表是性价比最高的部件**：同样 0.3 秒，深度从 5.0 掉到 2.7，胜率掉到 25%。
   因为它把"成五/挡四"这类强制着法从搜索里摘出来，直接砍掉大量无效分支。
2. **置换表在这个搜索深度下没有可测收益**（5.0 层 / 5973 vs 5888 节点，胜率 38% 对 62%）。
   这是一个诚实的负结果：置换表的价值要在更深的搜索或大量重复局面里才体现，
   0.3 秒 / 5 层还太浅。
3. **VCF 只影响"能不能算到强制胜"**（战术表里唯一失效项），对 9×9 快棋胜率影响不大（50%），
   因为浅层搜索本身也能看到简单的杀。

### 5.3 强化学习 vs 传统引擎

`bench_vs_teacher.py`：19×19、随机 4 手开局、网络 60 次模拟、传统引擎 0.1 秒/手。

| 训练轮数 | 局数 | 结果 | 胜率 |
| --- | ---: | --- | ---: |
| 1014 | 6 | 0 胜 6 负 | 0% |
| 1204 | 12 | 3 胜 9 负 | 25% |
| 1252 | 12 | 1 胜 11 负 | 8% |
| 1318 | 24 | 4 胜 20 负 | **17%** |
| 合计 | **60** | 12 胜 48 负 | **20%** |

### 5.4 一个值得记录的方法论错误

早期基准赛用 6 局，一度出现"16.7% 胜率"。后来发现：两个 agent 都是**确定性**的
（传统引擎无随机、网络取 argmax），所以 6 局其实是**同一盘棋重复 3 遍**（执黑 3 局、执白 3 局），
真实分辨率只有 2 盘棋。加上"每局随机 4 手开局"后，才得到上表里可信的数字。

## 六、局限与改进

**已知局限**

1. **强度**：强化模型对传统引擎只有约 20% 胜率。瓶颈是"看不见两级威胁"
   （活三→活四）——60~120 次模拟在 19×19 上等效深度只有 3~4 层，而 VCF 需要 6~10 层。
2. **速度**：纯 Python，19×19 每步 1~2 秒是天花板；同等强度下 C++/位棋盘能快一个数量级。
3. **尺寸迁移**：网络是全卷积的（权重与棋盘无关），但只用 19×19 训练，实测 9×9 上胜率
   从 25% 掉到 8%——感受野（19 格）远超 9×9 边长，价值头的全局池化尺度也错位。
4. **VCF 不完善**：只搜自己的杀，不搜对手的 VCF，也没有证明数搜索（df-pn）的残局求解。
5. **禁手**：四四按方向近似计数（同方向多个四算一个），极端棋形可能与正式连珠规则有出入。

**后续计划**

- 把传统引擎的威胁表接进 MCTS（树内强制扩展），做"RL 大局观 + α-β 战术"的混合体
- 有 GPU 后把网络加宽到 128 通道 × 8 残差块，并把对局模拟次数提到 400+
- 训练引入 9×9 → 15×19 → 19×19 的课程，改善小棋盘迁移

### 7.3 三个代表性协作案例（详见 `docs/AI协作记录.md`）

1. **采样温度误判**：AI 先建议把"温度采样的手数"从 8 加到 24，结果对局反而从 16 手缩到 12 手。
   用同一权重做 A/B 对照（只改温度）才发现真凶是 `τ=1.0`：12 手 → 20 手 → 36 手（τ=1/0.5/0.25）。
   结论：改参数前先做单变量实验。
2. **基准赛方法性错误**：AI 最初的 bench 是 6 局，但两个确定性 agent 会让同一盘棋重复 3 遍。
   发现后改成"每局随机 4 手开局"，此前的"0% / 16.7%"全部作废。
3. **one-hot 与剪枝的边界**：战术护栏对"成五 / 唯一挡四"（规则强制）可以写死成 one-hot 标签，
   但对"活三"（启发式）只能用来剪枝候选集，否则会把错误的标签灌进训练数据。

## 九、训练档案

`history/` 目录保存了强化模型的完整训练史，可以直接复盘"哪一步改动带来了什么变化"：

| 文件 | 内容 |
| --- | --- |
| `history/weights/` | **130 份权重快照**（iter 516 → 1363，每 30 分钟一份） |
| `history/训练记录.md` | 七个训练阶段的改动、动机与实测效果（含四条踩坑记录） |
| `history/timeline.csv` | 每份快照对应的完整配置 + 同期巡检指标 |
| `history/index.csv` | 快照索引与生成它的训练命令 |
| `history/monitor.csv` | 每小时健康巡检（单轮耗时、胜负、截断、手数） |
| `history/bench_log.csv` | 基准赛记录（强化模型 vs 传统引擎） |

七个阶段的核心结论：

- **纯 19×19 优于混训**（目标棋盘一致，样本不打折）；
- **手数上限 170 优于 150**（截断 3.8/8 → 1.5/8，平均手数 106 → 54）；
- **采样温度 τ=0.25 是关键**（同样权重：τ=1.0 平均 12 手，τ=0.25 平均 36 手）；
- 模拟次数 60 → 120 后 policy loss 从 2.27 降到 1.25，对传统引擎胜率从 0% 爬到约 20%。

**64 通道这条线已于 2026-11-02 封存在 2040 轮（最佳 1997）**：
对传统引擎始终停在 29~33%（48 局基准），四次尝试（提 sims、降 sims、三种战术补漏、sims 200 长跑）
都指向"30 万参数容量见底"。全量 401 份快照归档在仓库外的 `模型快照-64ch/`，
仓库内保留关键记录与两版权重。

随后进入**第五阶段：加宽网络（128 通道，119 万参数，从零训练）**。

这条线运行期间加了一套**代际闸门**（训练/部署分离）：

- 训练永远写 `checkpoints/latest.pt`（模型一直在动）；
- 每 50 轮让"最新"挑战"当前最佳"（40 局，黑白各 20），**胜率 ≥55% 才提升为最佳**；
- 部署读 `checkpoints/best.pt`，所以线上不会退步；
- 连续 3 次低于 50% 写 `gate_alert.txt` 报警；长期卡在 50%±5% 判为饱和。

交付权重 `iter 1477`：对传统引擎 **42%**（同一批 24 局），而 1608 只有 8%。
